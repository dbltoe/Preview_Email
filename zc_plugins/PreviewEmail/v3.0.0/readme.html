What It Does

Zen Cart sends a lot of email, and most of it you never see: the order confirmation goes to the customer, the status update goes to the customer, the low stock notice goes to a copy address. Preview Email puts all of it on one admin page, built from your own recent customers, orders and products, so you can look at each one as the customer will see it, in HTML and in plain text, and send yourself a test of any of them.

It lists:

  • Every email Zen Cart itself sends — not just the twelve that have template files. The store copies of the order, welcome, coupon, gift certificate and status emails; the low stock notice; Ask a Question; the pending-review notice; the newsletter; the admin password reset, the admin sign-in code, the admin-account-changed notice and payment module alerts.
  • The emails your add-ons send, found automatically when the add-on describes them (see For Plugin Authors). Descriptions ship here for Social Contact Footer, Admin Add Customer, Fraud Screen, Back in Stock and Recover Cart Sales, and appear only when that add-on is installed.
  • Your own custom emails, described in a small file under your admin directory.
  • Any template file nothing claims, so a stray email_template_something.html can still be looked at.

Installing

  1. Upload the zc_plugins/PreviewEmail/ directory into your store's zc_plugins/ directory, so that zc_plugins/PreviewEmail/v3.0.0/manifest.php exists on the server.
  2. Open Modules → Plugin Manager, select Preview Email and press Install.
  3. The page is at Tools → Preview Email.

Nothing else is created: no configuration group, no database table, one menu entry. Uninstalling from Plugin Manager removes it.

Upgrading From Preview Email 1.x or 2.x

Those versions were files copied into the admin directory plus an SQL patch. Install 3.0.0 as above; its installer removes the old previewEmail menu row so you do not get two entries. Then delete the old files from your admin directory:

<admin>/preview_email.php
<admin>/includes/functions/extra_functions/preview_email.php
<admin>/includes/languages/english/preview_email.php
<admin>/includes/languages/english/extra_definitions/preview_email.php

Keep custom_preview_email.php if you customized it; 3.0.0 still calls preview_email_custom(). A direct_test.html in the catalog root still supplies the direct-email body.

The Page

Across the top, four facts that decide whether a test can arrive, read from Configuration → E-Mail Options: whether sending is on, whether HTML email is on, the transport, and the template directory. Then the emails, in groups, each row showing the email, the zen_mail() module name, and the template file core will use for it. When an email has no template of its own and the default is what will be used, the row says so. A grayed row is an email this store cannot send right now, with the reason under it.

Previewing

Preview HTML opens a new tab with the message exactly as core would build it: the same template resolution, the same logo, footer and disclaimers. A strip at the top names the template file, the stylesheet core pours into it (normally email/email_common.css), any rules the template carries itself or inline styles in the template or message content, since those win over the stylesheet, and, most usefully, every placeholder in the template that nothing fills. Core does not remove those; they go out in the email as literal $NAME text. If you see one here, the template names something the sending code does not provide.

Preview text opens the plain-text part, derived the way zen_mail() derives it, disclaimers included. This is what a customer who chose TEXT-Only receives, and what every address the store does not know receives. A message that reads well as HTML can be a wall of link text in this form; it is worth a look.

Sending a Test

Type an address (your own admin address is filled in), choose HTML or plain text, and press Send test on any row. The message goes through zen_mail() with the store's real transport and settings, so what arrives is what a customer would get. One thing is different: the format you chose is applied to that one send, through core's own NOTIFY_EMAIL_DETERMINING_EMAIL_FORMAT notifier. Core normally sends plain text to any address it does not find in the customers table, which would make "send me the HTML" impossible for most admin addresses. Nothing about the recipient's stored preference is changed.

Tests are real sends, to the address you typed and nowhere else. A test of the store copy of an order goes to you, not to the copy address; nothing here ever sends to a customer. Each test is written to the admin activity log.

A refusal names the reason: sending off, HTML off, the module listed in EMAIL_MODULES_TO_SKIP, an invalid address, or the recipient having opted out.

Your Own Emails

Preview Email knows about an email because a definition describes it: a small PHP file that gives it a name, says which zen_mail() module it uses, and builds a sample. Put yours in <admin>/includes/email_preview/; every .php file there is read and must return a definition or a list of them.

<?php
if (!defined('IS_ADMIN_FLAG')) { die('Illegal Access'); }

return [
    'key'      => 'renewal_reminder',
    'label'    => 'Support renewal reminder',
    'describe' => 'Sent eleven months after a purchase.',
    'module'   => 'renewal_reminder',
    'build'    => static function (array $def): array {
        $customer = preview_email_sample_customer();
        [$subject, $text, $html] = my_store_build_renewal_email($customer['name']);
        return [
            'subject'  => $subject,
            'text'     => $text,
            'block'    => ['EMAIL_MESSAGE_HTML' => $html],
            'to_name'  => $customer['name'],
            'to_email' => $customer['email'],
        ];
    },
];

build returns what your real sender passes to zen_mail(): the subject, the text body and the block of template placeholders. Call the same function your sender calls and the preview is exactly your email. Helpers for sample data and language files are listed in docs/CUSTOMIZING.md. A store definition with the same key as a bundled one replaces it.

For Plugin Authors

Put a directory named email_preview/ in your plugin's version directory, next to manifest.php, with one or more definition files in it. Preview Email reads it whenever your plugin is installed and enabled, and lists your emails under your plugin's name. Nothing in your plugin needs to reference Preview Email; if it is not installed, the directory is never read. Group the definitions under your plugin's name and prefix the keys with it so they cannot collide with anyone else's.
